1. Launch and the first screen

Two things start at launch. The intro plays, and the platform bridge quietly asks the phone whether a Play Games or Game Center session already exists. That answer usually arrives while the intro is still on screen and nothing is listening yet, so the bridge keeps it. When the menu is built it does three things in a fixed order: it sends anything queued while offline, syncs the three saves (the current run, your scores and your games history), and then reads the answer it missed.

Queue before pull

Offline sessions are sent before the cloud is read, so the pull already includes them.

Login screen once

It appears only while no account exists: the first run, or after logging out.

Never blocks play

"Play as Guest" (or "Continue offline") is always shown and never disabled.

2. One handler for every answer

A button press, the launch check and an answer that turns up after the 30-second wait has expired all end in the same function, so it behaves the same whether or not the login screen is still showing. An answer that arrives on its own never binds an account: on a first run the login screen stays up, and a player who chose guest play stays a guest until they press sign in.

  • Failure while signed in means the session lapsed, so the main menu shows Reconnect to sync.
  • Pressed and nothing answers: after 30 seconds the buttons come back with a hint. On iOS the hint points to the device's Game Center settings, because once iOS stops offering its prompt, retrying in the game cannot help.
  • Already signed in on the device: pressing the button skips the platform prompt and goes straight to binding.

4. Offline play and the queue

Sign-in is never on the path to playing. A save that cannot reach the cloud is deferred, not failed, but only for a signed-in player. A guest has no cloud, so their device is the whole record.

  • The queue holds the latest copy of each save, not a log, and it survives the app being closed.
  • A partial send keeps whatever did not go through; nothing else in the queue is lost with it.
  • Signing in and logging out both clear the queue, because it does not record whose saves it holds.
  • While the phone reports no connection, the sign-in and sync buttons grey out with No internet connection. The menu re-checks every second and when the app comes back into focus. The guest exit is never greyed.

5. Log out and account switch

Saves belong to the account that earned them. Logging out moves them aside under that account's id rather than deleting them, so the next account starts clean and the original one gets everything back when it signs in again. A guest cannot log out: a guest id cannot be recovered, so the saves would be orphaned.

If the phone's own account changes under a signed-in install, the game asks before doing anything, naming both accounts. Declining pauses sync for the session and keeps the two accounts' progress apart. Neither platform lets an app end the system sign-in, so logout is local: pressing the provider button again re-binds straight away.

7. How two copies are reconciled

The save on the device is the source of truth and the cloud is a mirror. When both exist, the game picks without asking:

  • A finished run leaves a marker naming the run that ended. Another device holding that run deletes its copy instead of pushing it back.
  • Two different runs: the one started later is the live one.
  • The same run on two devices: the one further ahead (wave, then turn) wins, never the clock.
  • Scores and games history are merged entry by entry, so neither device's results are lost.
  • Anything else: the most recent write wins, and a tie keeps the device's copy.

Display names from Google or Apple are treated as untrusted text: control characters, direction overrides and invisible characters are removed, and every printable character in any script is kept.

Your progress lives on your device first; the cloud copy sits in your own Google or Apple account.
